# storefront

React + Vite. Static build, **no backend, no login**. The app talks to the
outside world in exactly two ways:

1. **Events** — user activity is queued in IndexedDB and flushed by a service
   worker to a configurable Lambda function URL (`send_event_now()` for the
   immediate path). Same `/add-events` contract as `../server_docs/`.
2. **Storage** — catalog + product JSON (`VITE_CATALOG_BASE`) and product media
   (`VITE_MEDIA_BASE`) are fetched at runtime; both default to the bundled
   `public/storage/`. Search / filter / sort run client-side. Cart and wishlist
   live in `localStorage`.

Installable **PWA** — web app manifest + Bare Brilliant icons (pulled from
barebrilliant.com) + an app-shell service worker with an offline fallback.

Design system follows `../raw_plans/BARE BRILLIANT WEBSITE.pdf` (the Final spec):
**Playfair Display + Inter**, dark-first (black / ivory / grey) with warm gold
`#B79A72` as a hairline accent only. Tokens + type scale in `src/theme.css`.

## Run

Package manager: **Yarn** (classic — `yarn.lock` committed).

```bash
cd storefront
yarn install
yarn dev              # http://localhost:8080
yarn build            # -> dist/
```

## Storage layout (`public/storage/`)

```
catalog/catalog.json                         facets + sorts + product cards
products/<product_id>.json                   full PDP payload (superset of the card)
products_media/<ix>_<hash6>_<w>x<h>.webp      gallery + thumbnail images
product_placeholder.webp                     fallback (spec spells it "produt_" — corrected here)
products_raw_media/                           drop untouched source uploads here; not read by the app
```

The sample data + placeholder images are **committed** (they are content, not a
build artifact) and regenerated by `yarn gen:catalog`
(`scripts/gen-sample-catalog.mjs`, uses `sharp`). Edit the `PRODUCTS` table in
that script and re-run, or replace the files directly. Product images are
**square (1:1)**; `object-fit: cover` absorbs off-square crops.

### Serving data + media elsewhere

Two independent bases so JSON and media can live on a static server / CDN
separately. Each falls back to `VITE_STORAGE_BASE`, then to the bundled
`public/storage/`:

| var | serves |
| --- | --- |
| `VITE_CATALOG_BASE` | `catalog/catalog.json`, `products/<id>.json` |
| `VITE_MEDIA_BASE` | `products_media/*`, `product_placeholder.webp` |

```bash
# both on a local static server for now:
VITE_CATALOG_BASE=http://localhost:8000/ VITE_MEDIA_BASE=http://localhost:8000/ yarn dev
```

A cross-origin host must send `Access-Control-Allow-Origin` for the JSON
`fetch`es (images load without CORS). The service worker never caches
`/storage/` or cross-origin requests, so product data is always fresh.

## PWA

- `public/manifest.webmanifest` — `display: standalone`, `start_url:
  ./?source=pwa`, relative `scope`/`icons` so it works at any base path.
- `public/favicon/` — real Bare Brilliant icons (`.ico`, 96px, apple-touch,
  192/512 maskable) pulled from barebrilliant.com; `favicon.svg` is a small
  hand-drawn mark (the live 2 MB SVG was skipped).
- `index.html` links them with `%BASE_URL%` so Vite rewrites the paths for the
  deployed base.
- The service worker (below) **precaches the app shell** into
  `bb-shell-<SW_VERSION>` on `install`, serves navigations **network-first**
  (→ cached shell → `offline.html`) and hashed `/assets/` + icons
  **stale-while-revalidate**, and drops its whole cache except the fresh shell
  on `activate` (deploy).

## Events (`src/events/`)

`../server_docs` contract. `trackEvent(...)` / named `track*` helpers →
IndexedDB → service worker delivers. Phase-2 adds the spec's shopping taxonomy:
`product_view`, `filter_change`, `sort_change`, `add_to_cart`,
`shortlist_saved`, `checkout_started`, `order_placed`.

`sendEventNow(...)` (alias `send_event_now`) is the immediate path: one PUT,
returns the body, **no retry** (it's the "give me the answer now" call). Used
for `lead_submitted` and `order_placed`; on failure the caller falls back to
`trackEvent`, and the durable queue below then handles delivery.

### Service worker delivery policy (`scripts/service-worker.template.js`)

- **Cadence** — the SW's own **10s** `setInterval` is the only regular flush.
  `trackEvent()` just writes to IndexedDB — it does **not** poke the SW, so a
  navigation / click does not trigger an immediate send. Background Sync
  (`flush-events`, registered **once per page load**) is the backstop for a tab
  that closes before the tick or a device that reconnects; `flushNow()` and
  `sendEventNow()` are the explicit "go now" paths.
- **Drains the whole queue** — each flush sends **every** queued event in FIFO
  batches of 50 (`MAX_BATCH_SIZE`), up to `MAX_BATCHES_PER_FLUSH` (2000
  events) per tick; anything beyond that waits for the next tick.
- **Per-batch retry** — a failed PUT (network error or non-2xx) is retried
  **3×** with exponential backoff: `1s → 2s → 4s` (`RETRY_DELAYS_MS`).
- **Circuit breaker** — if all 4 attempts fail, the whole pipeline pauses for
  **30 minutes** (`CIRCUIT_PAUSE_MS`). Every 10s tick during the pause is a
  no-op; events keep queuing (nothing lost); the failed batch stays queued
  (marked `status:"failed"`, `attempts` bumped). Pause state lives in the
  IndexedDB `meta` store so it survives the worker being killed and respawned,
  and is **reset on deploy** (`activate`) since a new build may have fixed the
  endpoint.
- **Idempotency** — the `Idempotency-Key` is derived from the batch's own
  IndexedDB keys, so every retry (and a post-pause retry) carries the same key
  and the backend can dedupe a lost-response resend.

`yarn test:sw` exercises all of the above (`scripts/sw-flush.test.mjs`, uses
`fake-indexeddb`).

## Build config & cache-bust

`scripts/gen-build-config.mjs` runs before `dev`/`build` and bakes a fresh
`SW_VERSION` + `VITE_LAMBDA_URL` into `public/service-worker.js` (git-ignored)
and `src/generated/buildInfo.js`. A new `SW_VERSION` each deploy → the browser
reinstalls the worker → `activate` wipes every cache and reloads open tabs, so
a changed bundle or Lambda URL always reaches clients.

## Deploy

`../.github/workflows/deploy.yml` runs `yarn install --frozen-lockfile && yarn
build` and publishes `dist/` (including `dist/storage/` and `dist/404.html`) to
GitHub Pages on push to `main`. Repo variables: `VITE_LAMBDA_URL`,
`VITE_TENANT_NAME`, `VITE_BASE` (optional), `VITE_STORAGE_BASE` (optional).
